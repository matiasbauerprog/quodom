# Quodom Web App (quodom-web/app/CLAUDE.md)

React 18 + Vite + TypeScript + plain CSS. 1:1 visual clone of the original React Native APP at `F:\backup\Command Soluciones\Quodom\APP` (read-only reference).

## Comandos
- `npm install`
- `npm run dev` — dev server en `http://localhost:5173` (requiere API en `http://localhost:3999`)
- `npm run build` — build de producción a `dist/`
- `npm run preview` — servir el build
- `npm run typecheck` — `tsc -b --noEmit`
- `npm run api-types` — regenera `src/api/schema.d.ts` desde `../api/openapi.yaml`. Correrlo cada vez que cambia el contrato; `tests/api-types.test.ts` falla si quedó viejo.
- `npm test` — Vitest (lógica no trivial y componentes con reglas que se rompen en silencio)

## Estructura
- `src/api/` — cliente `apiFetch` + un módulo por recurso. Todas las llamadas al backend pasan por acá. Los tipos de datos **no se escriben a mano**: `types.ts` son alias de `schema.d.ts`, generado desde `openapi.yaml`.
- `src/auth/` — `AuthContext` y `ProtectedRoute`. La sesión es una cookie httpOnly que pone el API; la app no ve el token, así que al cargar siempre pregunta `GET /users/current`.
- `src/guest/` — Quodom de invitado en `localStorage.quodom.guest`; `migrateGuestQuodom` lo transfiere al backend al iniciar sesión.
- `src/utils/telefono.ts` — `COD_AREA` ('011', fijo y deshabilitado en el formulario) y el teléfono de 8 dígitos, que se limpia mientras se escribe. Lo mismo lo valida el servidor (patrón en `openapi.yaml`); acá está para que el usuario se entere antes de guardar. Lo usan `SignUp` y `DetalleUsuario`, que son los dos únicos lugares donde se pide un teléfono.
- `src/quodom/bloqueosEnvio.ts` — qué impide enviar un Quodom, para no ofrecer un botón que el servidor va a rechazar con 409. `conFaltaConcreta` le pone nombre al motivo cuando quien lo muestra tiene las líneas cargadas ("elegí litros en Latex Interior Blanco Mate" en vez de "algún producto"): **cambia el texto, no la decisión**, que la sigue tomando el resumen porque es el que coincide con lo que va a contestar el backend. Dos entradas porque los dos lugares tienen datos distintos: el sidebar sólo tiene el resumen (`bloqueoDeEnvio`, mira `porccompletado`) y el detalle tiene las líneas (`bloqueoDeEnvioPorLineas`, mira cada atributo). **No es la validación**, que vive en el backend; acá se replica el mismo orden de prioridad para que el aviso coincida con la respuesta. `useTieneDireccion` arranca en `true` y se queda en `true` si la consulta falla, porque un `false` optimista trabaría el envío con un motivo que puede ser falso; se reconsulta con el evento `direcciones:changed`, que dispara `AgregarDireccion` — el sidebar vive en el `Layout` y no se desmonta al ir a cargarla.
- `src/quodom/DialogoProveedores.tsx` + `FilaProveedor.tsx` + `AvisoPuntoAproximado.tsx` + `ProveedoresContactados.tsx` + `useProveedores.ts` — los comercios cerca, en el momento de enviar. El diálogo lo abren **tres lugares**: los dos que envían —el pie del árbol (`MisQuodomsSidebar`) y el detalle (`DetalleQuodom`)—, que pasan `onEnviado`, y `DialogoPedido` (la ventana del historial), que lo abre sobre un Quodom **ya enviado** para sumarle otro proveedor y por eso **no** pasa `onEnviado`: el estado no cambia, así que no hay nada que recargar. Los dos que envían pasan `onEnviado` porque el Quodom **no se muda de sección por código**: sale del árbol porque el backend lo pasó a `ENVIADO` y alguien disparó la recarga. **`QuodomCard` no envía**: tuvo un `enviable` que abría el diálogo adentro de la tarjeta y que sólo pasaba su test, y se borró en vez de cablearse porque ese montaje es el que `MisQuodomsSidebar` se reestructuró para evitar (en Mis Quodoms el refresco de después del envío desmonta la tarjeta y cierra el diálogo a mitad del flujo). Seis reglas, cada una con su síntoma:
  - **"Enviar sin elegir proveedor" está en los tres estados** del diálogo: con lista, con lista vacía y con la búsqueda caída. Antes de este feature el comprador siempre podía enviar, y eso **no lo puede romper una API ajena**. Por lo mismo el diálogo no se cierra al enviarle a uno: mandarle a varios es para lo que existe.
  - **Un solo renglón para las dos superficies.** `FilaProveedor` lo dibujan el selector del envío y la sección del Quodom ya enviado, porque sus tres situaciones de teléfono están medidas contra Google —`telefono` abre WhatsApp, `telefonovisible` sólo se llama (un 0800 es válido y no recibe WhatsApp), y sin ninguno queda "ver en Maps"— y una segunda copia se despega de la primera a la primera corrección.
  - **El botón "No se envió" vive sólo en el selector** (`permiteDeshacer`): escribe `sin_whatsapp`, que es un dato **global, permanente y sin fecha** por `place_id` que leen las listas de todos los demás compradores. En el momento es una observación; en el historial, días después, es un recuerdo —y lo que ahí se quiere decir suele ser "no me contestaron"—, así que un toque degradaría a ese comercio para todo el mundo.
  - **Una búsqueda por apertura y ninguna recarga** (`useProveedores`): cada llamada es una búsqueda **paga** con tope de 10/min, y lo que cambia al enviar o al deshacer es un valor que ya se conoce, así que se parchea local. Recargando, cada envío costaba dos búsquedas (tres desde el detalle) y, cuando esa recarga fallaba por el tope, el proveedor que acababa de recibir el Quodom aparecía como no contactado y el comprador le mandaba otra vez. Por lo mismo la sección del detalle **no se monta después de usar el selector en esa visita**: repetía con una búsqueda paga la lista que el comprador tenía delante.
  - **El aviso de "distancias desde el centro de la localidad" y el `desde` del encabezado están en las dos pantallas**, y el aviso es **un solo componente** (`AvisoPuntoAproximado`, con un `Link` a `/direcciones` y **no un `href`**: un ancla recarga el documento entero en medio de un envío y se lleva el Quodom a medio mandar). La promesa es que la pantalla nunca muestra una distancia medida desde otro lugar que el que nombra, y el historial la rompía: mostraba "0,4 km" sin decir desde dónde, y 0,4 km del centro de Villa Ballester pueden ser 3 km de la casa.
  - **El error de la búsqueda está escrito para una persona** (`mensajeDeBusqueda`): el texto del servidor se conserva **sólo en el 429**, que lo escribió este repo para esta pantalla. Los demás son diagnóstico (`places: HTTP 503 {...}`, o una instrucción sobre el dashboard de Render cuando falta la clave) y es justo el modo de falla para el que existe la salida de emergencia.

  En desarrollo, **StrictMode monta cada diálogo dos veces y eso son dos búsquedas pagas por apertura**. Es sólo en dev (en el build no pasa), pero cuenta para la factura mientras se trabaja: no dejar el diálogo abriéndose en un loop de recarga en caliente.
- `src/screens/MisQuodoms/DialogoPedido.tsx` — un pedido del historial, de **sólo lectura**. Tocar una tarjeta del historial abre esta ventana en lugar de navegar al detalle: irse de la pantalla para mirar un pedido y volver pierde el lugar en la lista, y `DetalleQuodom` es la pantalla de **editar**, que sobre un enviado no va — el proveedor cotiza sobre lo que recibió, y cambiarlo después deja al comprador creyendo que pidió otra cosa. Tres reglas:
  - **Un enviado tiene dos caminos que no se pisan.** *Enviar a otro proveedor* **no toca el pedido**: sigue `ENVIADO` y en el historial, y sólo se le suma un contactado (el caso normal: le mandé a uno, no me contestó, le mando a otro). *Volver a armado* crea un Quodom **nuevo** con las mismas líneas y lo deja abierto en el árbol de su rubro —eso es "volver al sidebar"—; el enviado **no se revierte**, porque revertirlo borraría la notificación y el historial de algo que sí pasó.
  - **Se monta al nivel de la sección, no dentro del `<li>`.** Montada adentro, el refresco de la lista desmonta la tarjeta y se lleva la ventana a mitad de un envío: es el mismo montaje que `MisQuodomsSidebar` se reestructuró para evitar y que `QuodomCard` tenía muerto.
  - **Repetir deja lo mismo por los dos caminos.** El botón del bloque "Repetí un pedido" y el *Volver a armado* de la ventana llaman los dos a `abrirQuodom`: si uno lo hiciera y el otro no, repetir daría resultados distintos según dónde se tocó.
- `src/quodom/quodomAbierto.ts` — el mapa `{idrubro: idquodom}` en `localStorage.quodom.abierto`: qué Quodom de cada rubro recibe lo que se agrega y a la vez cuál está desplegado en el árbol. Es estado del cliente y no del servidor a propósito (dos pestañas pueden diferir y al backend no le importa), así que **se sanea contra la lista viva**: `sanearAbiertos` descarta lo que ya no está en armado. Sin eso, un Quodom borrado o enviado en otra pestaña seguiría figurando como abierto y el próximo `+` iría a un id muerto; con el saneo se trata como "ninguno abierto" y se pregunta de nuevo. Un valor corrupto en el storage se lee como mapa vacío.
- `src/quodom/ramas.ts` — agrupa la lista plana en ramas por rubro para el árbol, y **es el único lugar donde se filtran los rubros retirados para el árbol** (la migración de invitado y `DetalleQuodom` filtran por su cuenta con `rubrosDisponibles`/`rubroDisponible`). El filtro no vive en el componente porque `rubroDisponible` es asíncrono: filtrar adentro del árbol comparaba contra una promesa y no filtraba nada, sin error. Por eso `ramasDeQuodoms` recibe `disponibles` ya resuelto y sigue siendo síncrona y testeable. Un rubro retirado que se cuela se ofrece como destino y el servidor lo rechaza con 400 recién al soltar.
- `src/quodom/useQuodomsEnArmado.ts` — el cargador compartido por el panel derecho y la barra inferior. Tres reglas, cada una con su síntoma:
  - **`Promise.allSettled`, no `all`**: Quodoms y rubros son preguntas distintas. Con `all`, que falle la lista de rubros tira abajo también los Quodoms y el usuario ve el árbol vacío con trabajo en curso.
  - **Si falla sólo la lista de rubros, el árbol sale sin filtrar** (`disponibles = null`), no vacío. Mostrar todo es seguro porque el backend rechaza un rubro retirado; mostrar nada parece pérdida de datos.
  - **`sanearAbiertos` sólo tras una carga de Quodoms que de verdad salió bien.** Con una lista vacía por error de red, el saneo creería que no queda nada en armado y cerraría todo lo que el usuario tenía abierto: vuelve a preguntar destino en todos los rubros.
  Además sólo se aplica la respuesta del pedido más reciente, y un refresco fallido no pisa lo último bueno.
- `src/components/QuodomCard.tsx` — **dos estados y no tres**: `En armado` y `ENVIADO`. Hubo un tercero, **VENCIDO**, que aparecía a las 72hs de enviado ("Pasaron las 72hs y se venció tu pedido"): es herencia de Quodom 1.0, donde los vendedores tenían ese plazo para cotizar. Acá no hay vendedores ni cotizaciones y **nada vence** — el pedido sale por WhatsApp y el proveedor contesta cuando puede. No existía en el backend ni en el contrato, sólo en ese archivo, así que a los tres días un pedido perfecto se leía como fracasado; lo reportó el usuario mirando su propio historial. Con `onAbrir` la tarjeta no navega al detalle sino que avisa a quien la puso — lo usa el historial para su ventana.
- `src/components/layout/ArbolQuodoms.tsx` — **un solo árbol** que dibujan las dos superficies: `.mq-sidebar` (desde 1025px) y `.barra-quodom` (debajo), que nunca conviven. No lo copies para una de ellas. Los destinos del arrastre se reconocen por `data-destino` (el id del Quodom) + `data-rubro`, y la zona de "+ un Quodom nuevo" por `data-nuevo` + `data-rubro`: el arrastre hace hit-test buscando exactamente esos atributos, así que si se renombran o se pierden el arrastre sigue andando sin error y simplemente no encuentra destino. Tres reglas que no se ven en el render:
  - **En el Quodom abierto los atributos van en la raíz de `TarjetaDestino`, no en su cabecera.** La tarjeta abierta mide varias veces el alto de su cabecera (lleva las líneas y el pie de envío), así que con los atributos en el botón, soltar sobre las líneas no encontraba destino.
  - **`data-nuevo` existe sólo mientras se arrastra y sólo en el rubro del producto.** Antes estaba siempre en el DOM y lo escondía el CSS; ofrecerlo en los otros rubros era ofrecer un 409.
  - **El rubro de la URL (`?rubro=`) sube al tope y se resalta.** Se lee acá adentro y no entra por prop porque las dos superficies tendrían que leer lo mismo para pasárselo. Con ocho rubros, el del catálogo podía quedar fuera de vista.
  - **Cambiar de rubro acomoda el árbol una sola vez por rubro** (`rubroAcomodado`): pliega los demás y, si el rubro tiene un único Quodom y ninguno abierto, lo abre. Las dos cosas que lo hacen frágil: corre **sólo en el cambio** —si corriera en cada render, cerrar a mano el único Quodom lo reabriría en el acto— y **no corre con `ramas` vacío**, que es "todavía no cargó": acomodar ahí daría por hecho que el rubro no tiene Quodoms y no se volvería a intentar cuando lleguen.
- `src/components/layout/TarjetaDestino.tsx` — la tarjeta blanca del Quodom que recibe lo que se agrega, sobre el panel oscuro. La usan el árbol (para el abierto de cada rubro) y el sidebar (para un carrito de invitado, con el chip "Sin guardar" en vez del verde). El contraste es lo que contesta "¿a dónde va el próximo `+`?", que antes se insinuaba con un verde tenue y no se decía en ningún lado.
- `src/components/layout/RotuloRubro.tsx` — el rubro como rótulo con línea, compartido por el árbol (donde pliega, y lleva `data-rubro-cab`) y por los carritos de invitado (donde es fijo). Bajarle el peso al rubro es lo que deja al Quodom como lo único que parece tocable.
- `src/quodom/arrastre.ts` — arrastrar una tarjeta sobre el árbol, **sólo con mouse** (`pointerType`): el árbol donde se suelta es el panel de escritorio, así que en celular el gesto no tenía dónde terminar y lo único que lograba era comerse el scroll de la lista. Va con **eventos de puntero y no con el drag-and-drop de HTML**: `dragstart` congela una imagen de la tarjeta y no deja animarla, y el efecto de achicarse al entrar en el destino es imposible con esa API. **Todo camino de salida termina en `limpiar()`**, que saca los oyentes de `window`, el fantasma y la clase `arrastrando` del body: soltar (`terminar`) y abortar (`abortar`, un envoltorio de `limpiar`). Abortan `pointercancel`, `blur`, Escape, un `pointermove` con `buttons === 0` (el `pointerup` se perdió) y el evento `arrastre:abortar`, que hoy sólo despacha `ListaProductos` al desmontarse. Sin `limpiar`, un `pointerup` perdido dejaba el arrastre vivo y el siguiente clic en cualquier lado ejecutaba un soltado. Si agregás un oyente de `window`, sacalo en `limpiar`. El rechazo de un rubro distinto es **del cliente**: compara ids de rubro y pinta `arrastre-rechaza`; el 409 `rubro_mismatch` del servidor es la red de seguridad para lo que pase de ahí.
- `src/quodom/useArrastreActivo.ts` — qué producto se está arrastrando (`arrastre:inicio` / `arrastre:fin`), para que el panel lo nombre y apague los rubros donde no se puede soltar. Son eventos de `window` y no un contexto porque `arrastre.ts` no vive en el árbol de componentes: lo arranca una tarjeta del catálogo y lo escuchan el sidebar y la barra inferior, que cuelgan del `Layout`.
- `src/quodom/DialogoDestino.tsx` lleva además la **ficha del producto** (`producto`: imagen, descripción y los atributos con el valor ya elegido). Está ahí porque en el catálogo este diálogo es lo que abre el clic en el producto, así que es el único lugar donde se ve qué es el producto antes de mandarlo a algún lado. Falta —y el diálogo va sin cabecera— donde quien lo abre no tiene esos datos: el buscador trae sólo imagen y nombre, y un `+` que encoló varias líneas no tiene **un** producto que mostrar.
- `src/quodom/DialogoDestino.tsx`, `useDestinoLote.ts` y `conAbierto` (en `agregarProducto.ts`) — **una sola regla de destino** para una línea suelta y para un lote (propuesta del asistente, lista subida): ir al abierto del rubro sin preguntar, y si no hay (o resultó muerto: `conAbierto` lo olvida ante un `ApiError`, no ante un error de red), preguntar una vez. Tanto la cola de `useAgregarProducto` como `useDestinoLote` **retoman, no reinician**: sacan cada ítem del lote apenas llega, y reutilizan el Quodom ya creado. Si reiniciaran, tras un fallo a medias lo que ya entró entraría otra vez y el usuario vería líneas duplicadas.
- `src/styles/` — `tokens.css` (paleta, tipografías, espacios, radios), `reset.css`, `typography.css`, `utilities.css` (`.container`, `.card`, `.btn`, `.hoja`, `.pantalla-header`, `.pantalla-contenido`), `global.css` que las importa todas.
- `src/components/layout/` — `AppBar`, `Drawer`, `Layout`, `BarraQuodomInferior`, `AppBarBack`, `ArbolQuodoms` (ver `src/quodom/` abajo).
  - `BarraQuodomInferior` es el panel en celular, y **está siempre**: es la única entrada que hay, y esconderla cuando no hay nada deja al que recién llega sin ver que el panel existe. Lo único que espera es la primera respuesta, para no decir "ninguno" un instante antes de mostrar los que hay. Su etiqueta habla **del rubro que está en pantalla** (`?rubro=`), no de todos los abiertos: listándolos, en celular decía "Sumando a: Limpieza" todo el tiempo, incluso navegando Pintura.
  - `PanelVacio` son los tres pasos, compartidos por las dos superficies: dos copias del mismo texto se despegan a la primera corrección. No nombra arrastrar, que en celular no existe.
  - `Layout.css` mide con **`dvh` y no `vh`**, y le reserva 72px abajo al `main`. Con `vh` el layout queda más alto que la pantalla del celular (no descuenta la barra de direcciones) y la barra fija cae debajo del borde visible hasta que uno scrollea; sin el `padding-bottom`, lo último de cada pantalla queda abajo de ella.
  - `Drawer` lleva la **cuenta de enviados** al lado de "Historial de pedidos". Es la referencia de que un Quodom pasó al historial: al cotizar, el backend lo pasa a `ENVIADO` y el árbol lo pierde, pero nada decía adónde fue. En escritorio el menú está siempre a la vista, así que el árbol pierde uno y el historial gana uno en el mismo momento. Escucha `quodom:changed`, el mismo evento del árbol, o la cuenta queda vieja justo cuando importa; tiene su propia consulta como la campanita (`useQuodomsEnArmado` ya corre dos veces y una tercera copia del mismo estado es peor que un pedido más a nuestra API); y si falla, no se muestra y el menú sigue siendo un menú. Va en **gris y no en rojo**: en este panel un círculo rojo ya se leyó una vez como alerta, y acá no hay nada que atender.
  - `ManijaPanel` es el borde entre el catálogo y el panel derecho, que el usuario arrastra para ensancharlo (sólo escritorio; doble clic vuelve al 30%, flechas con teclado). Vive en una columna de ancho cero del grid de `.layout` y escribe `--ancho-panel` **directo en `<html>` mientras se arrastra**, sin estado de React: con estado, cada `pointermove` re-renderizaba el `Layout` entero, panel incluido. Los topes (300px y la mitad del layout) están dos veces a propósito, en el componente y en el `clamp` de `Layout.css`: el del CSS es el que protege cuando la ventana se achica después de guardado. Por eso mismo **las grillas del contenido no pueden contar columnas por el ancho de la ventana**: la de productos es `auto-fill` en escritorio, y con 6 fijas la última quedaba cortada debajo del panel ancho.
  - `AppBar` es la única barra: lleva la hamburguesa y, salvo en el home pelado, el logo QUODOM, que es el camino de vuelta al inicio.
  - `AppBarBack` **no es una barra**: es el título de la pantalla con su flecha. Va sólo en las pantallas anidadas —Mis datos, Cambiar contraseña, Nueva y Editar dirección, detalle del Quodom—, donde la flecha es la salida real. Las que se llegan desde el menú escriben su propio `h1` (ver abajo).
- `src/components/CampoDireccionMapa.tsx` — busca la dirección en el mapa y la entrega desarmada. El corte en 3 caracteres y el debounce de 350ms son **control de gasto** (cada consulta se le paga a Google), y el token de `sesion` agrupa la tanda de tecleo con el detalle final para que Google no la cobre aparte: se renueva recién cuando el usuario elige. **Rellena los campos del formulario, no los reemplaza** — quedan visibles y editables porque Google no siempre trae la altura y nunca el piso, y sin clave configurada el buscador responde 503 y la carga a mano es el único camino. Los tipos salen de `types.ts` (alias del contrato), no escritos a mano.
- `src/components/DialogoMapa.tsx` + `mapaGoogle.ts` — la ventana con el pin arrastrable, para corregir el punto de una dirección. `mapaGoogle.ts` es **el único lugar del proyecto donde una clave de Google vive en el navegador**: `VITE_GOOGLE_MAPS_BROWSER_KEY`, distinta de la del servidor y restringida por dominio, porque una variable `VITE_` se hornea en el bundle. El SDK se inyecta **una vez por sesión** y la promesa se reusa: abrir y cerrar la ventana cinco veces no son cinco cargas pagas. Cuatro reglas:
  - **Sin clave la ventana lo dice y no bloquea**: la carga a mano es el camino que queda, igual que con el autocompletado. Lo mismo si el script no carga — el `onerror` suelta la promesa, porque dejarla pendiente deja el esqueleto para siempre y sin reintento.
  - **Se consulta la dirección en `dragend` y en el clic del mapa, nunca durante el arrastre**: cada consulta es paga y arrastrar dispara decenas de eventos.
  - **Lo que se confirma es el punto del pin.** La respuesta del servidor trae `lat`/`lng` como se pidieron, y la dirección es la confirmación; `aplicarDelPin` guarda `punto_manual: true` y **no toca el `placeid`**, que en la inversa es el de la dirección más cercana y no el del punto.
  - **Si no se puede leer la dirección, el punto se confirma igual.** El punto es lo que el usuario vino a arreglar; los campos de texto ya los tiene escritos, y se rellenan sólo si la inversa trae algo (pisarlos con `''` sería borrarle lo que estaba bien).
- `src/components/` — `Loader`, `EmptyState`, `ErrorState`, `Notificaciones/CampanitaNotificaciones` (hoy sin montar: salió de la AppBar en el rediseño).
- `src/components/Notificaciones/NotificacionesQuodom.tsx` — la campanita al lado de "Mis Quodoms" (panel de escritorio y barra de celular), con el número de no leídas. El registro lo hace el backend al cotizar (`QUODOMENVIADO`); esto sólo lo muestra. Abrir el menú **marca todas como leídas**. Cada notificación de un Quodom que todavía existe ofrece tres caminos: *Historial* (`/mis-quodoms?pedido=<id>`: lleva a la **pantalla** y no a la ventana —así lo pidió el usuario—, y `ListaMisQuodoms` resalta esa tarjeta, baja hasta ella y saca el parámetro de la URL), *Repetir* (igual que "Volver a armado": `repetir` + `abrirQuodom`) y *Otro proveedor* (sólo si está `ENVIADO`). Tres reglas:
  - **Se recuenta con `quodom:changed`**, el evento que dispara el envío: así el número aparece en el momento en que el Quodom sale del árbol, sin polling. Las dos copias (panel y barra, una escondida por CSS) se emparejan con `notificaciones:leidas`.
  - **El selector de proveedores se monta afuera del menú**: el menú se cierra al elegir, y montado adentro se llevaría el selector a mitad de un envío (la misma regla que `MisQuodomsSidebar` y `DialogoPedido`).
  - **El menú se ubica contra la cabecera, no contra el botón** (`.notq` no es `relative`): toma todo el ancho del panel, que es lo que hace entrar las tres acciones; con el panel angosto la tercera baja de línea. Los tests que montan el panel o la barra mockean `api/oper_notificaciones`, o sale un fetch real.
- `src/screens/` — una carpeta por área (Auth, Home, Quodom, MisQuodoms, Profile, Direcciones, Notificaciones); cada screen tiene su `.tsx` + `.css` al lado.
- `src/router/routes.tsx` — árbol de rutas con `createBrowserRouter`; rutas públicas fuera del `<Layout>` y rutas de app dentro.
- `tests/` — Vitest + happy-dom + Testing Library: api client, guest, migración y paridad con el contrato, más tests de componente y de módulo junto al código en `src/**/__tests__/` (ver Testing).

## Reglas visuales (mobile-first, en este orden)
1. **Base mobile (< 601px):** escribí siempre primero para pantalla chica; grillas de 1–2 columnas, layout apilado, drawer que abre/cierra.
2. **Tablet: `@media (min-width: 601px) and (max-width: 1024px)`** — ampliá grillas a 3–4 columnas, aumentá padding lateral (`.container` va a 720px máx).
3. **Desktop: `@media (min-width: 1025px)`** — el drawer se vuelve persistente (grid `260px 1fr` en `.layout`), `.container` a 1120px máx, más columnas en grillas de productos/categorías.

Reglas duras: nunca fijes anchos en píxeles a nivel de página; usá `.container` + porcentajes/grid. La forma de hoja (`border-top-left-radius: 8px; border-bottom-right-radius: 8px`) va en tarjetas, imágenes y botones grandes (clase `.hoja`, ya aplicada por `.card` y `.btn`). Paleta: `--color-fondo #F1F1F1`, `--color-acento #E63946`, `--color-exito #2DAB66`, `--color-texto #1A1A1A`, `--color-tarjeta #FFFFFF`, `--color-panel-oscuro #1E1E2A` (para sidebars, drawer header y barra inferior).

Fuentes: Prompt para títulos y botones (`--font-prompt`), Work Sans para texto (`--font-work`), Jaldi/Montserrat disponibles por si algún componente puntual lo necesita.

`--color-whatsapp` (#25D366) es sólo para el botón que abre WhatsApp: lleva la marca de a dónde lleva, y no es `--color-exito`.

**Lo que carga y ya tiene forma conocida va con esqueleto, no con spinner** (`.esqueleto` en `utilities.css`). Las tabs de subcategoría y la grilla de productos dibujan tantos bloques como piezas reales y del mismo tamaño. Con el spinner centrado las dos colapsaban a una línea y volvían a aparecer, y ese salto hacía que cambiar de rubro se leyera como una recarga de toda la página.

### Cómo se arma una pantalla de sección

Mis Quodoms, Perfil, Direcciones y Notificaciones se llegan desde el menú y tienen que arrancar todas igual. Antes cada una traía su propia regla de encabezado, idénticas entre sí y ya separándose en los márgenes, así que la forma vive en `utilities.css` y no repetida en cada CSS:

```
<section className="container mq">
  <div className="pantalla-header">        h1 a la izquierda, acción al otro extremo
  <div className="pantalla-contenido">     el cuerpo, agrupado en un solo bloque
```

El envoltorio del contenido **no es decorativo**: sin él, el reparto de la sección sería entre cada pieza suelta —el error, el loader, la lista— y quedaría desparejo según qué esté visible en cada momento. Con él, la sección reparte entre dos bloques con `space-evenly`.

Tres medidas compartidas, en `tokens.css`, para que ninguna pantalla se despegue distinto que las demás:

| | |
|---|---|
| `--pantalla-top` | dónde empieza el contenido bajo el header: `clamp(48px, 8vh, 120px)`, proporcional con piso y techo |
| `--pantalla-ancho` | 720px. `.container` llega a 1120px, que necesita una grilla de productos y le sobra a una lista |
| `--pantalla-alto` | la ventana menos el header, contra el cual se reparte la sección |

El `h1` de una pantalla es `--fs-h1` (32px). Los 44px de antes eran tamaño de wordmark; el del home es aparte (`.home-wordmark`).

### El home tiene dos perillas, no una

`--home-inicio` decide dónde arranca el wordmark y `--home-aire` cuánto se separan los elementos. Estaban fundidas en un `space-evenly`, que reparte el sobrante en partes iguales —una arriba del wordmark y una entre cada par—, así que juntar los elementos subía el wordmark y no había forma de tener una cosa sin la otra.

## Convenciones
- **UI:** español (mensajes, labels, estados).
- **Código:** inglés (nombres de identifiers, comentarios). Sin comentarios salvo cuando el "por qué" no sea evidente.
- **HTML semántico:** `header`, `nav`, `main`, `section`, `article`, `button`, `label`+`input`.
- **Errores del API:** los controllers backend responden `{ res: false, message }` con status 4xx; el cliente lanza `ApiError` con el `message` — mostrarlo tal cual.
- **Persistencia local:** el Quodom de invitado, el mapa de Quodoms abiertos (`quodom.abierto`) y el ancho del panel derecho (`quodom.anchoPanel`, ver `ManijaPanel`); nada más. **El token de sesión nunca va a `localStorage`**: vive en una cookie httpOnly que ningún script puede leer.
- **El API se llama siempre por `/api`, en el mismo dominio que la app** (proxy de Vite en dev, regla de rewrite en Render). No apuntar `VITE_API_URL` a `quodom-api.onrender.com`: para el navegador sería otro sitio, Safari descarta la cookie y nadie con iPhone puede iniciar sesión.
- **Testing:** el recorrido visual se hace siempre en el navegador (dev server + API real) — es lo que valida layout, contraste y sensación de uso, y ningún test lo reemplaza. Además se escriben tests de Vitest sobre el comportamiento: tanto lógica pura (api client, guest quodom, migración) como componentes con Testing Library, cuando hay una regla que se puede romper en silencio — qué se llama y con qué argumentos, qué se muestra en cada estado, qué pasa cuando el servidor falla. No se testea el aspecto.
