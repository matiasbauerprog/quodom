# Quodom Web API (quodom-web/api/CLAUDE.md)

Express + Sequelize 6 + SQLite, JavaScript (CommonJS). Port 1:1 de la API original sin vendedores ni pagos.

## Comandos
- `npm install` — instalar dependencias
- `npm run seed` — poblar `quodom.sqlite` desde `Documentacion 2.0/Categorias/Migracion.xlsx` (verifica 50 subcategorías / 644 productos)
- `npm run guias` — regenera `src/config/guias/<idrubro>.txt` desde `informacion para la ia/<Rubro>/Listado_*.xlsx`. **Correrlo cada vez que se toca una planilla**: sin eso la API sigue mandándole al asistente las instrucciones viejas y no falla nada visible. Ver §8 de `claude.md` en la raíz.
- `npm run migrar-empresa` — agrega a `users` las columnas `empresa`, `cuit` y `facturaA` y deja el `codArea` en `011`. **Correrlo una vez sobre cualquier base que ya exista**: `model.sync()` crea una tabla que falta pero nunca hace `ALTER` sobre una creada, así que sin esto el modelo declara columnas que la base no tiene y guardar el perfil falla. Es idempotente y no borra ninguna cuenta (`ADD COLUMN` no toca las filas).
- `npm run migrar-multi-quodom` — dropea el índice único parcial `quodom_abierto_por_rubro`, que imponía un Quodom `CREADO` por usuario y rubro. **Correrlo una vez sobre cualquier base que ya exista**: `model.sync()` nunca hace `ALTER` sobre una tabla creada, así que sacar el índice del modelo no toca una base existente. Si se saltea, el modelo dice que se pueden tener varios Quodoms por rubro y el segundo `POST /quodom/create` falla por el índice único de SQLite en esa base y sólo en ella (ya no con el 409 de antes); con la base de tests, que se crea de cero, no se nota. Es idempotente. Después, como siempre que cambia el schema, hay que commitear `quodom.sqlite` y verificar el blob (§6 de la raíz).
- `npm run migrar-direccion-mapa` — agrega a `users_direcciones` las columnas `placeid`, `lat`, `lng` y `coords_actualizado`. **Correrlo una vez sobre cualquier base que ya exista**: `model.sync()` nunca hace `ALTER` sobre una tabla creada, así que sin esto el modelo declara columnas que la base no tiene y guardar una dirección falla. Es idempotente y `ADD COLUMN` no toca las filas, así que ninguna dirección se pierde. Después, como siempre que cambia el schema, commitear `quodom.sqlite` y verificar el blob (§6 de la raíz).
- `npm run migrar-proveedores` — crea `quodom_proveedores` y `lugares_sinwhatsapp` en una base que ya exista. Es la única migración donde `model.sync()` **sí** alcanza (crea una tabla que falta; lo que nunca hace es `ALTER` sobre una creada), y el script existe igual para dejar el paso explícito, hacer `wal_checkpoint(TRUNCATE)` y poder verificar lo que se despliega. Después, como siempre que cambia el schema, commitear `quodom.sqlite` y **verificar el blob commiteado y no el archivo local** (§6 de la raíz) — y en Windows extraer ese blob a una **ruta nativa**, no a `/tmp`: node no entiende la ruta de Git Bash, `sqlite3` crea ahí una base vacía y la verificación pasa en falso (§9 de la raíz).
- `node scripts/verificar-direcciones.js` — chequeo **manual** de la geocodificación, con la clave real y a costo de unas consultas. No es un test y no corre con la suite: existe porque ningún test puede saber si una dirección real cae en el punto correcto. Correrlo después de tocar `direccionDeGoogle.js` o `provinciasGoogle.js`.
- `node scripts/verificar-proveedores.js "<localidad>"` — el hermano del anterior, para los **términos de búsqueda** de proveedores: toma la localidad por parámetro (los términos se chequean por zona), lee `src/config/rubrosPlaces.js` —así que lo que se prueba es lo que corre en producción— y por cada rubro activo imprime los comercios con nombre, puntuación, reseñas, distancia y teléfono, marcando los cinco que vería el comprador. **Usa la clave real y gasta plata en cada corrida**: una consulta del nivel caro por rubro activo más una para ubicar la localidad; sin `GOOGLE_MAPS_API_KEY` se niega a arrancar y no consulta nada. No es un test y no puede serlo: si "papelera" devuelve papeleras o cestos de basura lo juzga una persona mirando. Mirar que sean del rubro, que haya al menos tres, y cuántos salen sin teléfono. Es el ciclo de calibración de §9 de la raíz: editar el término, correr esto, mirar. **Conviene apuntar `DB_STORAGE` a una copia**: abre la base configurada y le corre `sync()`, que por defecto es `quodom.sqlite`, la que se commitea y se despliega.
- `npm run dev` — servidor en `http://localhost:3999` (nodemon). **`openapi.yaml` se lee una sola vez, al arrancar** (`helpers/openapi.js`), así que `nodemon.json` declara `"ext": "js,json,yaml"` para que tocar el contrato reinicie el server. Sin eso el server sigue validando contra el contrato viejo y una **ruta nueva no existe para el validador**: sus query params llegan como no declarados y los rechaza con 400 nombrándolos — el síntoma es *"Faltan datos o hay datos inválidos: lat, lng"* sobre campos que están perfectos, con los tests en verde porque cada suite levanta su propia app. Ya costó una sesión de diagnóstico.
- `npm test` — Jest + Supertest contra SQLite en memoria (`--runInBand`; cada archivo de test tiene su propia DB)
- `http://localhost:3999/docs/` — la documentación navegable del API, sólo con `npm run dev` (`nodemon.json` pone `API_DOCS=true`). En Render no existe.

## Estructura
- `src/server.js` — app Express; exporta `app` (los tests la importan sin levantar el puerto)
- `src/routes/` → `src/controllers/` → `src/models/` + `src/helpers/db.js`
- `src/helpers/views.js` — vistas SQL (`v_Busquedas`, `v_Quodoms`, `v_Quodoms_Lines`, `v_InfoCompradors`). Los modelos `v_*` NO se sincronizan (son vistas); NUNCA usar `sequelize.sync()` global.
- `src/middleware/encodeQuerySpaces.js` — vuelve a codificar los espacios literales de la query, **antes** del validador. En Render el sitio le habla al API por una regla de reescritura `/api/*` (tiene que ser el mismo origen: la sesión es una cookie y Safari descarta las de otro sitio), y **esa reescritura reescribe el `%20` de la query como `+`**, que es la codificación de formulario, y el contrato lo rechaza con *"Parameter 'q' must be url encoded"* — el `+` está en su lista de reservados, el espacio no. **El middleware toca `originalUrl` además de `url`**, porque el validador lee `url.parse(req.originalUrl).query`: un primer intento cambió sólo `url`, la suite quedó verde y en producción no cambió nada. El cliente codifica bien; lo que rompe está en el medio. Rompía **todo texto libre** — el autocompletado de direcciones (`q`) y la búsqueda de productos del home (`b`), que con dos palabras daba 400 en producción y andaba perfecto en local. **Local no lo ve**: el proxy de Vite reenvía la URL tal cual, y los tests entran por `app` directo, así que es invisible para todo el desarrollo. Medido el 2026-10-15.
- `src/middleware/auth.js` — `verifyToken()` / `isAdmin()`. Leen el JWT de la cookie `quodom_session` (`helpers/session.js`) o, si no está, del header Bearer, que queda para tests y herramientas. Un token con `action` (link de blanqueo o de validar email) **nunca** abre sesión.
- `/users/signin`, `/signup`, `/reset`, `/reenviar`, `/changePass` y `/validateReset` tienen límite de intentos por IP (y por casilla, los que mandan mail). Los topes se ajustan con `AUTH_LIMIT_*` y la IP del cliente se obtiene salteando los proxies conocidos (`src/config/proxies.js`), no contando saltos: la cantidad cambia según se entre por la app o directo.
- `src/config/guias/` — guías por rubro **generadas**; no editarlas a mano, se pisan con `npm run guias`. La fuente son las planillas en `informacion para la ia/`.
- `src/helpers/gemini.js` — cadena de modelos con respaldo, reparto del presupuesto de tiempo y tope de salida. El modelo por defecto está elegido por medición, no por ser el más nuevo.
- Los endpoints de `/lugares` (autocompletado, detalle y **el punto del mapa**) comparten un balde con **dos topes**: `LUGARES_RATE_LIMIT_PER_MINUTE` (40) y `LUGARES_RATE_LIMIT_PER_DAY` (300). El de por minuto acota el ritmo y no el total — 40/min sostenidos son 57.600 consultas pagas en un día, y un bucle de recarga en caliente llega solo. Cada uno con su mensaje: el del día no se arregla esperando un rato, así que nombra la salida (cargar la dirección a mano).
- `src/helpers/places.js` — el **único** archivo que habla con Google Places, igual que `gemini.js` con Gemini: dueño del `fetch`, timeout propio y clave desde el entorno. Maneja tres máscaras de campos y **la máscara fija el precio de toda la consulta**, así que la de direcciones no lleva ningún campo caro, la de proveedores lleva puntuación, reseñas y teléfono juntos (pedir el teléfono aparte es otra consulta al mismo precio) y la de un punto lleva sólo ubicación. Alrededor hay tres piezas puras, separadas del HTTP a propósito —se prueban con tablas y sin simular a Google—: `rankearProveedores.js` (distancia y orden, que Google no da; la penalización por reportado es `-0.15` y no `-1`, que con el puntaje acotado en `[0,1]` era una expulsión), `telefonoWhatsapp.js` (el formato que abre WhatsApp y el 0800, que no lo recibe; **no** afirma fijo contra celular, que en Argentina no se puede saber de un número sin el `15` — medido sobre 21 teléfonos reales; y el mapeo de un lugar de Places que comparten el endpoint y `scripts/verificar-proveedores.js`) y `puntoDelQuodom.js` (los dos niveles de precisión y la caché de 30 días). Los términos de búsqueda, en `src/config/rubrosPlaces.js`, son la perilla; el ciclo de calibración está en §9 de la raíz.
- Config por `.env` (ver `.env.example`). Nunca commitear `.env`. **`quodom.sqlite` sí se commitea** y es la que se despliega: es la de §6 de `claude.md` en la raíz, con la trampa del modo WAL (verificar el blob commiteado, nunca el archivo local).

## Convenciones
- Errores tipo string lanzados desde controllers → el error-handler responde `{ res: false, message }` (400/404).
- Rutas públicas (guest): `/categorias`, `/productos/categoria/:id`, `/productos/:id`, `/busqueda`, `/provincias`, `/localidades/prov`. Todo lo demás requiere token.
- Estados de Quodom: `CREADO` → `ENVIADO` (vía `GET /quodom/whatsapp/:id`). No existen estados de cotización. Ese endpoint es el único que cambia el estado, así que **las condiciones para enviar se validan ahí**: sin productos (400), con alguna línea sin el atributo que su producto declara (409 `falta_atributo`) o sin ninguna dirección cargada (409 `falta_direccion`). Un bloqueo deja el Quodom en `CREADO` y no genera notificación. La dirección se resuelve al enviar y se guarda, porque `iddireccion` se copió al crear y puede estar en `null` aunque el usuario ya tenga una. Ver §3 de `claude.md` en la raíz.
- **Quodoms por rubro:** `GET /quodom/activos/:idrubro` (lista de los `CREADO` de ese rubro) reemplazó a `/quodom/activo/:idrubro`, que devolvía uno o `null`. `POST /quodom/create` y `POST /quodom/repetir/:id` **ya no responden 409 `rubro_duplicado`**: crean siempre. Lo que se mantiene es 409 `rubro_mismatch` al agregar una línea a un Quodom de otro rubro. Cuál Quodom está "abierto" lo decide el navegador, así que no hay endpoint ni columna para eso. Ver §3 de `claude.md` en la raíz.
- **Proveedores:** `GET /quodom/proveedores/:id` devuelve hasta cinco comercios del rubro del Quodom cerca de su dirección, y `POST /quodom/proveedores/:id/no-enviado` deshace un contacto. Las dos rutas van montadas bajo `/quodom/proveedores` y **antes** de `/quodom`, cuyo `/:id` se comería la primera. El GET consulta a Google y tiene **cupo propio** (balde `proveedores`, separado del chat de IA porque compartiéndolo buscar proveedores gastaba el cupo del chat), con dos topes: `PROVEEDORES_RATE_LIMIT_PER_MINUTE` acota el ritmo y `PROVEEDORES_RATE_LIMIT_PER_DAY` el total —sin el diario, una cuenta sostenida en 10/min son 14.400 búsquedas pagas por día— y cada uno con su mensaje, porque el del día no se arregla esperando un rato. El POST no consulta nada y no lleva cupo.
  - La respuesta es la **unión** de la búsqueda de hoy con los que el comprador ya contactó: un contactado que hoy no vuelve a salir llega con `sindatos: true`, sin nombre ni distancia (sólo se archiva su `place_id`), porque el historial existe para contestar "a quién le mandé". De Places se guarda **sólo el `place_id`**; nombre, puntuación y teléfono se vuelven a pedir cada vez, y un test lo afirma en negativo sobre las dos tablas (ver §9 de la raíz).
  - `motivo: 'sin_whatsapp'` suma el reporte global por `place_id` **sólo si el lugar fue ofrecido y contactado** (`orden` + `contactado_en`). `lugares_sinwhatsapp` es global, permanente y no se puede deshacer, y sin esa guarda cualquier sesión lo escribía en bucle con placeids sacados de Maps: el endpoint no consulta a Google, así que a propósito no tiene cupo que lo frene.
  - Un rubro activo **sin término** no rompe: se avisa en el log y se devuelve lista vacía con `preciso: true` (no se miró la dirección; con `false` la pantalla acusa a una dirección que está bien), porque es un olvido de configuración y no un caso del usuario.
  - Las coordenadas de una dirección son **caché de 30 días** y `puntoDelQuodom` es el que la lee: vencidas, una dirección del mapa se vuelve a resolver por su `place_id` (que sí es permanente) y una cargada a mano por su localidad.
- Tests: integración con la DB real en memoria, sin mocks. Cada feature nueva agrega su archivo en `tests/`.
- **Una ruta nueva o cambiada empieza por `openapi.yaml`.** Sin eso falla `tests/openapi.coverage.test.js` (ruta sin describir) o la validación de respuestas. Ya no hay esquemas Joi: la validación de pedidos sale del contrato. Si un campo vacío tiene que significar "no tocar", va `omitEmpty([...])` en la ruta, porque el contrato deja pasar `''` y `null`.
- Todo campo que un handler lea del body tiene que estar declarado en el contrato: el validador borra los que no lo están.
